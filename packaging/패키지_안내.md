# WATERCAST 설치 패키지 안내 (2026-10-23) — 세명소프트 배포 담당자용

이 묶음이 무엇으로 이루어져 있고, 어떤 순서로 설치·확인·교체하는지 한 장으로 정리했다.
자세한 명령과 장애 대응은 같은 디렉터리의 **`배포_실행순서.md`**, 새 서버(Ubuntu 24.04·새 세대 GPU)에 처음부터 올리는 순서와 GPU 판정은 **`현장_배포_절차.md`**, 운영·API 설명은 **`README_설치.md`**, 통합 플랫폼 연계 항목은 `연계정리_이노뎁_2세부.md` 를 본다.
정확한 버전·파일 목록·체크섬은 `MANIFEST.json` 과 `SHA256SUMS` 에 있다(`./install.sh` 가 자동으로 검증한다).

## 1. 요청하신 세 가지에 대한 대응

| 요청 | 패키지에 들어 있는 것 |
|---|---|
| 배포 스크립트 + 명령어 위주 실행 순서, 오류 로그가 보이게 | `install.sh`(7단계) 와 `배포_실행순서.md`. 모든 스크립트가 `logs/<스크립트>_<시각>.log` 에 출력을 남기고, 실패하면 **멈춘 명령·줄 번호·로그 파일 경로·컨테이너 로그 30줄**을 화면 마지막에 찍는다 |
| 배포 후 확인 스크립트 | `postcheck.sh` — 환경·설정·컨테이너·API·스모크 18개 등 27개 항목을 점검하고 `logs/postcheck_<시각>.txt` 보고서를 남긴다. 실패가 있으면 보고서 끝에 컨테이너 로그 200줄을 붙인다 |
| 사용자가 설정해야 할 것(데이터 경로·키) | 아래 5절 표. 경로는 묶음 디렉터리 기준으로 고정이라 따로 지정할 것이 없고, 키는 기상청 자료 수집용 `KMA_API_KEY` 하나뿐이며 **선택**이다. **우리 API 에는 인증이 없다** — 설치 뒤 바로 호출한다 |

## 2. 패키지 구성 — 런타임 컨테이너 + 앱 바이너리 + 탐지 엔진 (패키지 하나)

| 구성 요소 | 내용 | 언제 교체하나 |
|---|---|---|
| `images/watercast-runtime-<버전>.tar.gz` (약 1 GB) | 플랫폼 런타임 컨테이너 이미지: Python 3.11 + 의존성 + docker CLI. **앱 코드 없음** | 의존성(requirements)이 바뀔 때만 |
| `images/wbms-0.13.tar.gz` (11 GB) | **수체 탐지 엔진** 컨테이너 이미지(시립대 인수, TensorFlow 2.14·CUDA 11.8). `install.sh` 가 자동 적재 | 시립대가 재빌드본(CUDA 12.8+)을 주면 교체 |
| `app/watercast-app-<버전>-<빌드>.tar.gz` (약 90 MB, +`.sha256`) | 앱 바이너리: API·화면·지역 자료·스크립트 + `VERSION.json`(version·build·git·runtime_image) | 코드가 바뀔 때마다 — 이것만 받아 `./update_app.sh` |
| `data/incoming/handover/` | 탐지 모델 가중치(`03_model`) · 전처리 입력 영상 22장(`05_l1_pre`, 새 영상을 넣는 위치의 본보기) · 보조자료 DEM 등(`06_aux`) · 융합 번들 · 기상 CSV | — |
| `data/wbms_runs/` | 이미 탐지한 18장면의 마스크 캐시 | — |
| `backend/data/` | 쓰기 영역(잡 상태·규약 산출물·사용자 지역·예측 결과). 설치 때 비어 있다 | — |
| `src/` | 호스트에서 직접 탐지할 때 쓰는 러너(python3 표준 라이브러리만) | — |
| 스크립트 10개 | `install.sh` `postcheck.sh` `gpu_check.sh` `update_app.sh` `start.sh` `stop.sh` `status.sh` `smoke_test.sh` `uninstall.sh` `detect_scene.sh` | — |
| `docker-compose.yml` · `.env.example` · `docker-compose.smss-net.yml` | 실행 정의와 설정 틀(3세부 공유 네트워크 오버레이 포함) | — |
| `README_설치.md` · `배포_실행순서.md` · `현장_배포_절차.md` · `패키지_안내.md`(이 문서) · `연계정리_이노뎁_2세부.md` | 문서 | — |
| `MANIFEST.json` · `SHA256SUMS` · `logs/` | 버전·체크섬·로그 | — |

컨테이너는 `app/current`(앱 묶음을 풀어 둔 곳)를 `/app` 으로 마운트해 실행한다. `GET /api/v1/health` 의 `build` 가 지금 도는 앱 묶음의 build 를 알려 준다.
새 위성 영상이 들어오면 API 컨테이너가 호스트 docker 로 탐지 엔진 컨테이너를 띄워 탐지 → 면적 → 수위 → 예측 → 납품 파일까지 한 번에 만든다. 전부 이 패키지 하나로 된다(탐지 엔진을 뺀 시연용 lite 묶음은 따로 요청할 때만).

## 3. 명령어 순서

```bash
# 설치 (서버, 10분 안쪽)
tar -xzf watercast-<버전>-<날짜>.tar.gz && cd watercast-<버전>-<날짜>
cp .env.example .env && vi .env     # 5절 표. 포트가 비어 있고 uid 가 1000 이면 그대로 둬도 된다
./install.sh                        # 요구사항 → 체크섬 → .env → 런타임·탐지 엔진 이미지 load → 앱 묶음 → 기동 → 스모크 18개
./postcheck.sh                      # 배포 후 확인 30개 → logs/postcheck_<시각>.txt
./gpu_check.sh                      # 탐지를 GPU 로 돌릴 수 있는지 판정

# 운영
./status.sh   ./start.sh   ./stop.sh   ./smoke_test.sh   ./uninstall.sh [--images] [--data]

# 코드만 바뀐 앱 바이너리 교체 (이미지 그대로, 1분)
cp watercast-app-<버전>-<빌드>.tar.gz* app/
./update_app.sh app/watercast-app-<버전>-<빌드>.tar.gz    # 체크섬 → app/current 교체(이전은 app/prev) → 재기동 → 헬스 → 스모크
./update_app.sh --rollback                                # 문제 시 직전 build 로 복귀
```

## 4. 배포 후 확인 — `postcheck.sh` 가 보는 것

A 환경: docker 데몬·compose v2·python3·디스크 10 GB·(선택) GPU 툴킷
B 설정·디렉터리: `.env`, `app/current` 의 build, 쓰기 디렉터리 5개, 탐지 캐시 장면 수, (선택) RUN_AS 와 산출 디렉터리 소유자 일치
C 컨테이너·포트: 두 컨테이너 healthy(최대 90초 대기), 이미지 태그 일치, API·업무 UI 포트 응답, (선택) 컨테이너→docker 소켓, 탐지 엔진 이미지·모델 가중치·입력 영상·보조자료
D API: health·버전·build 일치, 지역 목록, 수위 전망 호출, 오류 응답 형식(422 + 한국어 사유 + `X-Request-ID`), 최근 오류 조회, 화면 3개, (선택) 서버 오류 로그 0건
E 스모크 테스트 18개(헬스·지역·장면·마스크 다운로드·수위·면적·전망·탐지 잡 캐시·규약 파일명·화면 4종·오류 봉투·시 단위 API)
마지막 줄이 `결과: 통과 N · 실패 0` 이면 된다. 브라우저 확인 주소: `http://<서버>:18000/docs`, `/simple`, `/app`, `/eval`, `http://<서버>:8501/`.

## 5. 설정 항목 (`.env`) 과 데이터 위치

| 항목 | 기본 | 설명 |
|---|---|---|
| `WATERCAST_API_PORT` / `WATERCAST_UI_PORT` / `WATERCAST_PIPE_PORT` | 18000 / 8501 / 8502 | 포트가 겹치면 변경 |
| `WATERCAST_NAME` | watercast | 같은 서버에 두 벌 띄울 때 컨테이너 이름 접두 |
| `COMPOSE_PROFILES` | demo | 발표용 데모 화면(8502)이 필요 없으면 비운다 |
| `RUN_AS` | 1000:1000 | 묶음을 푼 계정의 `id -u`:`id -g` 와 같게(탐지 산출물 소유자) |
| `HOST_ROOT` | 비움(=이 디렉터리) | 보통 그대로 |
| `WBMS_GPU` | auto | GPU 있으면 GPU, 없거나 실행이 실패하면 CPU 로 자동 재시도 |
| `KMA_API_KEY` | 비움 | **선택.** 기상청 공공데이터포털 일반 인증키 — 과거 기상 관측·단기예보를 새로 받을 때만. 없어도 예측·탐지·화면 전부 동작 |
| `BACKEND_LIAISON_LOG_URL` / `_SYSTEM_CODE` / `_ALGM_ID` | 비움 / SC000000 / AG000000 | 통합 플랫폼이 알고리즘 로그 주소·코드를 배정하면 채운다. 비면 로그를 보내지 않는다 |
| `WITH_SMSS_NET` / `SMSS_NET` | 0 / smss-net | 3세부 컨테이너와 같은 도커 네트워크로 직결할 때 1 |

| 데이터 경로(묶음 디렉터리 기준, 지정 불필요) | 뜻 |
|---|---|
| `data/incoming/handover/05_l1_pre/<센서>_pre/<yyyy>/<yyyymmdd>/Pre_Busan_<센서>_<yyyymmdd>T<시각>.tif` | **새 위성 영상(전처리 GeoTIFF)을 넣는 곳**. API 에서는 `pre_path=/app/data/incoming/...` 로 부르거나 `pre_file` 로 업로드한다 |
| `data/wbms_runs/wb/<yyyy>/<yyyymmdd>/` | 탐지 결과 마스크(캐시) |
| `backend/data/scenes/<지역>/<장면>/` | 장면별 산출(규약 파일 `PT000003_*.tif`, 면적·수위·예측·`level_forecast.json`) |
| `backend/data/wbms_products/` | 통합 플랫폼에 주는 규약 파일명 사본 |
| `backend/data/regions/` | 사용자가 추가·수정한 지역 |
| `logs/` | 설치·교체·확인 로그와 보고서 |

**인증**: 우리 API 에는 인증이 없다. `http://<서버>:18000/api/v1/...` 를 바로 부른다. 잘못된 요청은 `error.message_ko`(한국어 사유)와 `request_id` 가 든 JSON 으로 오고, 응답 헤더 `X-Request-ID` 로 로그에서 같은 요청을 찾는다.

## 7. 참고

- GPU 가 없거나 탐지 이미지가 그 GPU 에서 실행에 실패하면 CPU 로 자동 재시도한다(장면당 10분 내외). 잡 결과의 `warnings`·`gpu_fallback` 에 사유가 남는다. 새 세대 GPU(RTX PRO 5000 등)는 `./gpu_check.sh` 로 먼저 판정한다 — 탐지 이미지가 CUDA 11.8·cuDNN 8 빌드라 GPU 연산이 실패할 수 있고, 그 경우 CPU 로 운영하면서 이미지 재빌드를 요청한다. 플랫폼(API·화면·예측)은 GPU 를 쓰지 않는다.
- 문의할 때 같이 보낼 것: `logs/` 의 최신 `install_*.log`·`postcheck_*.txt`, `docker compose ps -a`, `cat .env`(키 값은 가려도 됨).
- 되돌리기: 앱만이면 `./update_app.sh --rollback`, 전체면 `./stop.sh` 뒤 이전 묶음으로 `./install.sh`.
