# 현장 설치 환경 점검 — Ubuntu 24.04.4 / Intel Xeon / RTX PRO 5000 / NVIDIA Driver 595.84 / CUDA 13.2 (2026-10-20)

사용자가 알려준 현장 사양에 대해, 지금 저장소·서버 구성에서 문제가 되는 부분과 대응을 정리한다. 수치·버전은 전부 실측(서버
`docker run --entrypoint python wbms:0.13` 로 확인)이며 추정은 "추정"이라고 적었다.

## 1. 결론 먼저

| 항목 | 현 구성 | 현장(Ubuntu 24.04 · RTX PRO 5000 · 드라이버 595 · CUDA 13.2) | 판단 |
|---|---|---|---|
| API 서버(FastAPI, numpy 추론) | CPU 전용, 어떤 GPU 도 안 씀 | 그대로 동작 | **문제 없음** |
| 수위 예측기(13종, 신경망 포함) | 서버는 numpy 추론만. 학습은 CPU 로도 수 초~수 분 | 그대로 동작 | **문제 없음** (GPU 학습은 선택) |
| 시 단위 전망·단기예보·댐 자료(2026-10-20 추가) | 순수 Python/numpy | 그대로 동작 | **문제 없음** |
| 수체 탐지 컨테이너 `wbms:0.13` (시립대 인수 이미지) | **Python 3.11.0rc1 · TensorFlow 2.14.0 · CUDA 11.8 · cuDNN 8** | RTX PRO 5000 은 Blackwell 세대(compute capability 12.x). CUDA 11.8 빌드 TF 2.14 + cuDNN 8 에는 이 세대 커널이 없다 | **GPU 추론 실패 가능성 높음(추정) → CPU 로 돌아감**. 이미지 재빌드 필요 |
| 수위 산출 컨테이너(③ calc_wlwa, 같은 이미지) | CPU 연산 | 그대로 동작 | 문제 없음 |
| docker GPU 전달 | 백엔드가 호스트 docker 에 `--gpus device=0` 로 실행 | `nvidia-container-toolkit` 설치·`nvidia-ctk runtime configure` 필요 | 설치 항목 |
| 호스트 OS | 현 서버 Rocky Linux 9.6 | Ubuntu 24.04.4 | compose·스크립트는 배포판 무관. `docker compose` v2 필요 |

즉 **플랫폼(API·화면·예측)은 그대로 쓰고, 수체 탐지 GPU 가속만 이미지 재빌드가 필요**하다. 재빌드 전에는 CPU 탐지로 돌아가며
(부산 ICEYE 한 장면 CPU 10분 내외, 서버 실측 GPU 30~60초), 2026-10-20 에 **GPU 실행 실패 시 CPU 자동 재시도**를 넣었다.

## 2. 왜 GPU 추론이 실패할 것으로 보나

- 드라이버 595 는 최신이라 옛 CUDA 런타임(11.8)을 **구동 자체는 한다**(하위 호환). 문제는 커널 바이너리다.
- `wbms:0.13` 의 TensorFlow 2.14 는 CUDA 11.8 빌드로 sm_50~sm_90(+PTX) 를 담고, cuDNN 8 은 Blackwell(sm_120) 커널이 없다.
  합성곱이 cuDNN 을 타므로 `CUDNN_STATUS_NOT_SUPPORTED` / `no kernel image is available` 류로 죽을 가능성이 높다(추정 — 현장 GPU 가 없어 직접 확인은 못 했다).
- PTX JIT 로 일부 연산은 돌 수 있어도 성능·안정성을 보장할 수 없다.

## 3. 대응(우선순위 순)

1. **시립대에 재빌드 요청** — 같은 모델 가중치로 `tensorflow>=2.18`(CUDA 12.8+/cuDNN 9) 베이스. 이미지 태그는 `wbms:v1` 같은 새 태그로 받고
   `.env` 의 `BACKEND_WBMS_IMAGE`(또는 compose 의 이미지 변수)만 바꾼다. 모듈 CLI(`detect_water.py --gpu {cpu|gpu}` 등)가 같으면 백엔드 수정은 없다.
   재빌드 검증 절차: `docker run --rm --gpus device=0 --entrypoint python wbms:v1 -c "import tensorflow as tf; print(tf.config.list_physical_devices('GPU'))"`
   → GPU 가 보이면 `/simple` 새 영상 올리기로 한 장면 탐지(서버 실측 기준 30~60초면 정상).
2. **재빌드 전까지** `.env` 에 `WBMS_GPU=cpu` 를 두거나(명시적 CPU), `auto` 로 두고 자동 재시도에 맡긴다. 2026-10-20 추가:
   `backend/app/adapters/wbms_segmentation.py` — auto 모드에서 GPU 실행이 0 이 아닌 코드로 끝나면 `--gpus`·TF GPU 환경변수를 빼고
   `--gpu cpu` 로 한 번 더 돌린다(결과 `gpu_fallback{reason, note_ko}`, 연계 로그에 "GPU 실행 실패 → CPU 로 재시도" 1건).
   VRAM 프리플라이트(`BACKEND_WBMS_GPU_MIN_FREE_MIB`, 기본 3000)는 그대로.
3. **호스트 준비(Ubuntu 24.04)**: `docker` + `docker compose` v2, `nvidia-container-toolkit`(apt, NVIDIA 저장소) 설치 후
   `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`, 확인 `docker run --rm --gpus all nvidia/cuda:12.8.0-base-ubuntu24.04 nvidia-smi`.
   현 서버(Rocky 9.6, RTX 4090, 드라이버 575.57)에는 `nvidia-ctk`·`nvidia-container-runtime` 이 이미 있고 `docker info` 런타임에 `nvidia` 가 보인다 — 같은 상태를 만들면 된다.
4. **신경망 예측기 학습을 현장 GPU 로 하려면** `torch` 는 cu128 이상 휠(`pip install torch --index-url https://download.pytorch.org/whl/cu128`, torch ≥ 2.7)이어야 Blackwell 을 지원한다.
   서버 추론은 numpy 라 무관. 학습 시간은 지점당 수 분(CPU 도 가능).
5. **권한**: 호스트 사용자 uid:gid 를 compose `RUN_AS` 로 넘긴다(기본 1000:1000). 2026-10-03 서버에서 `/out/_logs` 권한 오류로 수위 산출이 죽은 사례는
   `_runner_writable()`(10-16 배포)로 막았다. Ubuntu 에서 첫 사용자 uid 가 1000 이면 기본값 그대로.
6. **메모리/디스크**: `wbms:0.13` 11.3 GB, 장면당 산출 수백 MB. 디스크 50 GB 이상 권장. RAM 은 CPU 탐지 시 8 GB 이상(서버 실측 기준 추정).

## 4. 현장에서 바로 돌려볼 점검 명령

```bash
# 1) GPU 가 docker 에서 보이는가
docker run --rm --gpus all nvidia/cuda:12.8.0-base-ubuntu24.04 nvidia-smi
# 2) 인수 이미지가 이 GPU 를 쓸 수 있는가 (실패하면 CPU 폴백 — 재빌드 요청)
docker run --rm --gpus device=0 --entrypoint python wbms:0.13 -c "import tensorflow as tf; print(tf.__version__, tf.config.list_physical_devices('GPU'))"
# 3) 플랫폼 기동
cp .env.example .env   # KMA_API_KEY, RUN_AS, WBMS_GPU 등 채우기
docker compose up -d --build && curl -s localhost:18000/api/v1/health
```
